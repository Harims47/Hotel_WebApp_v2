# Architecture Decisions Log

This document records the finalized architectural decisions for the multi-tenant **Restaurant OS** platform. These specifications form the foundation for database schema setup, backend API implementation, and security policies.

---

## 1. Final Tenancy Model
- **Decision:** Shared Database + Shared Schema, partitioned by `restaurant_id` (Tenant scope) and `location_id` (Outlet scope) on every operational table.
- **Rationale:** Minimizes server overhead and simplifies schema migrations via Alembic. Clean database isolation is guaranteed via PostgreSQL Row Level Security (RLS).

---

## 2. Final User Model
- **Decision:** Unified platform identity namespace combined with contextual tenant membership mappings.
- **Rationale:** A user has one global record in the `users` credentials table. Their operational rights are loaded dynamically from the `restaurant_memberships` table, enabling a staff member to work for different restaurants or locations.

---

## 3. Final RBAC Model
- **Decision:** Role mapping is defined in the `user_roles` table, which references a user's membership and is scoped to a specific `location_id` or scoped restaurant-wide (when `location_id IS NULL`).
- **Permissions:** Checked at runtime on the backend using role check dependencies on route handlers.

---

## 4. Final Location-Scope Model
- **Decision:** Scope is determined dynamically from the user's active context.
  - Waiters and Cashiers: Scoped to their single assigned `location_id`.
  - Area Managers: Assigned roles across multiple locations. They select their active context in the UI, which is validated on the backend.
  - General Managers: Scoped to all locations under their authorized `restaurant_id` (wildcard scope).

---

## 5. Final Menu Model
- **Decision:** Master Menu Categories (`menu_categories`) and Master Menu Items (`menu_items`) are defined at the **Restaurant** (tenant) level. Location-specific availability and price deviations are managed in the `menu_item_location_overrides` table.
- **Fallback Logic:** When querying the menu for a location, the system performs a `LEFT JOIN` from `menu_items` to `menu_item_location_overrides` on `location_id`. If an override price is present, it overrides the base price; otherwise, it falls back to the master price.

---

## 6. Final Inventory Ownership Model
- **Decision:** Scoped strictly to the **Location** level. Inventory items (`inventory_items`) are defined per restaurant, but their actual stock counts (`stock`) and movement ledgers (`stock_ledger`) are scoped to individual physical `inventory_locations` at outlets.
- **Transfers:** Multi-location stock transfers check that both location scopes belong to the same authorized tenant brand before executing atomic transaction updates.

---

## 7. Final Payment Model
- **Decision:** Support `CASH`, `UPI`, and `CARD` payment methods.
- **Implementation:** Checked via check constraints on the `payments` and `deliveries` tables: `CHECK (method IN ('CASH', 'UPI', 'CARD'))`.

---

## 8. Final Notification Model
- **Decision:** Server-driven notifications targeted to specific `restaurant_id`, `location_id`, `role`, or `user_id` scopes.
- **Fulfillment:** Transmitted in real-time via FastAPI WebSockets (backed by a Redis Pub/Sub channel). The client-side notification UI is simple and consumes socket streams securely.

---

## 9. Final Audit Model
- **Decision:** Scoped to `restaurant_id` and `location_id`. Write-only database triggers capture state differentials (`before_insert`, `before_update`) and commit them to the `audit_logs` table.

---

## 10. Final RLS Strategy
- **Decision:** Enforced at the database level on all multitenant tables.
- **Context passing:** FastAPI sets connection local parameters:
  - `SET LOCAL app.current_tenant_id = 'restaurant-uuid';`
  - `SET LOCAL app.current_location_id = 'location-uuid';` (or empty string/NULL for restaurant-wide GMs)
  - `SET LOCAL app.current_user_role = 'role-name';`
- **GM Wildcard Security:** If `current_location_id` is NULL, RLS strictly limits operations to the matching `restaurant_id` and checks that the user's role is indeed `GM`. It never allows global access. Platform Super Admin uses a separate bypass role.

---

## 11. Final Reporting Strategy
- **Decision:** Dynamic calculations without data duplication.
  - **Live stats:** Dynamic parameterized queries with indices.
  - **Operational summaries:** Dynamic aggregates over index dates.
  - **Analytical reports:** Asynchronous PostgreSQL Materialized Views refreshed overnight.

---

## 12. Final File Storage Strategy
- **Decision:** External object storage (e.g. AWS S3 or MinIO) with private access policies.
- **Retrieval:** Secured via temporary, signed URLs generated by the FastAPI backend on demand. No documents are stored in the database as bytea.

---

## 13. Final Configuration Strategy
- **Decision:** Decoupled into `restaurant_configurations` (brand properties) and `location_configurations` (outlet operating properties) tables.
- **Relational vs JSONB:** Settings that participate in query filters or access constraints (e.g. tax rates, operating hours, payment methods) are defined as explicit relational columns. JSONB is restricted to non-queryable variables (e.g. receipt footer templates).

---

## 14. Remaining Decisions
- **Offline Mode Strategy (V1 Status):** Resolved as strictly online-only for V1. Future sync mechanisms (IndexedDB vs. local SQLite) are deferred to a later iteration post-launch. No offline sync buffers are designed or implemented for the initial production launch.
